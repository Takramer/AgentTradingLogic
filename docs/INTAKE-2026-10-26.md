### Does the wallet trade the rule in the post?

Partly. Three checks against the stated rule:

- **Buy band 5–60¢:** 1,541 of 2,169 buys sit inside it; 565 (**26%**) sit above
  60¢ and 63 below 5¢.
- **"Under $25":** the median fits; the tail does not.
- **Timing:** buys spread evenly over all 24 UTC hours. They do not bunch after
  the GFS or ECMWF run releases. That fits an hourly poll across many time zones,
  as claimed, but does not prove a revision trigger.
- **Exits:** 767 of 850 sells fill at ≥90¢. The wallet sells near certainty
  instead of holding to settlement — a detail the post leaves out.

So: a real, profitable weather book of about the size claimed, with the stated
rule as a plausible but unconfirmed description of it.

### Why this does not reopen the August rejection — and what it does reopen

[WEATHER-REJECTED-2026-08-22.md](WEATHER-REJECTED-2026-08-22.md) measured the
**level**: the Kalshi ladder's implied expected high is unbiased and its error
already sits at the free model's floor. That still holds.

The post makes a different claim: the price is right *on average* but **lags
when the forecast is revised.** August never measured that lag. It is a speed
question, not an accuracy question, and the August data cannot answer it.

What answering it would take, with no trade:

1. Log the trial first: `py -m rhengine.trials log --family weather --label
   "Polymarket temperature price lag after ≥0.5°C forecast revision" --source
   docs/INTAKE-2026-10-26.md`.
2. Each hour, for ~10 cities: pull the Open-Meteo GFS and ECMWF next-day high at
   the settlement airport, and the Polymarket order book for every bracket.
3. When the forecast moves ≥0.5 °C, record the ask on the bracket one degree
   toward it, then every hour until settlement.
4. Score: after the 30 bps-equivalent spread and any fee, does buying at the
   first ask after a revision beat the settled value? Report trading days,
   not fills (failure #3).

Three weeks of capture, then one number. **Blocker before any trading, not before
measuring:** whether this account may legally trade Polymarket from the US. That
is a check for Thomas, not code.

### Status — capture built 2026-10-26

The plan above became `rhengine/weather_lag.py`. Where it differs from the plan,
the build wins:

- **Trial logged first**, family `weather`, kind `timing`, with the full entry
  and pass rule in the note. The ledger had **no** weather rows even though
  [WEATHER-REJECTED-2026-08-22.md](WEATHER-REJECTED-2026-08-22.md) says two were
  logged; they were backfilled as one `n=2` row. The family is now 3 trials, so
  the bar is **t ≥ 2.39**, and it needs **≥ 40 settled city-days**.
- **Every city, not ~10.** Gamma's `daily-temperature` tag lists ~257 open
  events; the first capture took 247 across 48 cities (high and low, °C and
  °F). Hong Kong is skipped (settles from the Observatory, not a METAR
  station), as are a few stale May events.
- **Settlement station from the market itself**: the ICAO id in
  `resolutionSource` (e.g. EGLC, KLGA), coordinates from aviationweather.gov.
- **Fees are zero**: every captured bracket reports `feeType: zero_fees`,
  `rate: 0`. The rate is captured each hour so a change shows up.
- **Entry rule as the post states it**: one bracket from the *old* forecast's
  bracket toward the new one, ask 5–60¢. The ask one capture earlier is kept
  too, so `score` also reports whether the price had already moved.

Run it:

```bash
python3 -m rhengine.weather_lag capture
python3 -m rhengine.weather_lag status
python3 -m rhengine.weather_lag settle
python3 -m rhengine.weather_lag score
```

Hourly: `scripts/weather_lag.plist` (launchd, capture then settle). Not
installed — loading it needs Thomas's hand; the commands are in the file. Each
capture is ~545 KB (~13 MB/day), so `capture.jsonl` is gitignored. A sleeping
Mac skips hours. `tests/test_weather_lag.py`: 13 tests, no network.

## C. The "Opus 5.5 + Jev trading bot" prompt — read, not run

Jev is TypeSafe AI's model: it takes typed questions about market state and
returns calibrated probabilities, not text (one secondary source; no official
docs found). TradingAgents v0.5.1 already uses it to screen social posts.

The prompt gets three things right, and this repo already has all three:
**models advise, code decides** (`alpha/live.py::emit` writes
`orders_permitted: false` for any book not exactly `autonomous`); hard limits
and a kill switch in code ([GOLIVE-RUNBOOK.md](GOLIVE-RUNBOOK.md)); and
point-in-time inputs only.

Where it breaks:

1. **Its gate cannot tell skill from luck.** "Sharpe > 1.5 over two years" has
   a standard error of √((1 + ½·1.5²)/2) ≈ 1.03, so the 95% interval runs from
   about −0.5 to +3.5. Even this repo's much longer panel gives ±0.5
   ([VIDEO-INTAKE-2026-08-17.md](VIDEO-INTAKE-2026-08-17.md) §Gap 1).
2. **"Self-improvement" re-runs the same gate on the same data every night.**
   Each rewrite is another draw. After a month the survivor is the maximum of
   ~30 tries — Cluster G, and failure #4 — and nothing in the prompt counts the
   tries.
3. **Per-candle decisions overlap.** Their calibration and Kelly sizing assume
   independent bets (failure #3).
4. **Jev's latency buys nothing here.** The engine trades daily bars; a
   sub-second scorer has nothing to score between closes.
5. It installs a third-party harness ("AgenKit") with one command. Not verified;
   do not run it in this repo.

### Kronos — park it, with the test written down

It forecasts OHLCV paths from past bars alone. If anyone wants it measured:
log a trial first, score its next-month forecast as a cross-sectional signal on
the PIT S&P 500 panel, **long-only**, through `alpha/book.py`, and judge the
t-stat against the family-wise bar. The prior is poor: price-only large-cap
signals run ~7 bp/month post-2005
([EXTERNAL-RESEARCH-2026-07.md](EXTERNAL-RESEARCH-2026-07.md) §0), and both local
holdouts are spent (hard rule 4), so even a pass would be an in-sample number.
Check the Hugging Face weights' licence before downloading.
